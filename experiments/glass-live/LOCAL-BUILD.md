# GitHub source, isolated local Windows build

The owner explicitly selected this workflow for subsequent development:

1. Read, edit and commit source and build scripts directly on GitHub.
2. Synchronize the reviewed exact commit into the custom worktree using a clean,
   fast-forward-only update. Never reset, clean, overwrite local edits, or patch
   local source independently of GitHub.
3. Compile and run the approved offscreen checks on the local Windows toolchain,
   in an output/cache directory outside every registered worktree and the live
   installation. The original and native worktrees are not build destinations.
4. Return synthetic render evidence and necessary build logs to the review chat.
5. Treat deployment as a separate, explicitly controlled operation after review.
   Never normally launch a staging EXE: normal client initialization can refresh
   the Windows startup entry. Only the early `--liquid-glass-self-test` entry is
   allowed to execute from the build directory.

This workflow does not require changing GitHub billing or registering the user's
computer as an Actions runner. The current push/PR commits use `[skip ci]` while
local verification is selected. Do not convert skipped/pending cloud checks into
success or bypass repository merge requirements. Do not move the existing
`liquid-glass-baseline-2026-09-15` tag.

## Reusable entry point

After exact synchronization, run `build-isolated.ps1` in a separate Windows
PowerShell 5.1-or-newer process, with `-NoProfile`. Required arguments:

- `-ExpectedCommit`: the full 40-character GitHub commit being built.
- `-BuildRoot`: a dedicated path such as `D:\proj\glass-isolated`; it must be
  separate from all registered worktrees and from the installed client.
- `-ProductionExe`: the currently installed client's path, used only to verify
  that its bytes have not changed during this build.
- Optional `-Jobs 2`: bounded compilation concurrency; default two jobs.
- Optional `-AttachEvidence`: emit a terminal `[UPLOAD FILE]` marker for the
  generated review ZIP, which the owner's Agent attaches to the current chat.

The script does not perform Git synchronization itself. The caller must pin and
verify the remote SHA, fast-forward the custom worktree, parse the downloaded
PowerShell script, and then invoke it with that same SHA.

## Isolation and output

`BuildRoot\target` is a persistent, dedicated Cargo cache. An exclusive file lock
prevents two instances of this entry point from sharing it concurrently. Each
invocation creates a new `r-<sha>-<random>` directory for logs, evidence and a
copied formal EXE. The first build may need to fill the new dependency cache;
subsequent builds can reuse it. No `cargo clean`, process-name kill, installed
EXE replacement, startup update or voice-settings write is performed.

The script uses `--locked`, explicit `--target x86_64-pc-windows-msvc`, and explicit
`--target-dir` arguments. Cargo may retrieve locked dependencies from the network;
this is not a claim that compilation itself is offline. Render self-tests use
only generated byte-validated textures, not screenshots or microphone input.

## Tests actually selected

The library test executable is compiled/listed first, without executing any test
body. The following three test suffixes must resolve uniquely in that executable;
each runs by its complete name with `--exact --test-threads=1`, and must report
both its specific PASS marker and exactly one executed/passed test:

- `actual_production_adaptive_contracts`: current adaptive material entrance,
  settled background response, exterior shadow, palette, same-time theme pairing,
  reduced-motion and zero hidden alpha.
- `current_adaptive_voice_states_and_review_frames`: current adaptive voice states,
  level sensitivity, lens ablation, same-time restoration and rapid background
  reversals; also exports real-HLSL frame sequences with synthetic time inputs.
- `all_production_states_use_actual_optics`: retained reference voice states and
  original 20-bar cyan-to-blue waveform palette, including byte-readback validation.

Formal client tests are compiled using `--no-run` (not advertised as executed).
The formal release EXE is built and copied to the new output directory, then only
its `--liquid-glass-self-test` path is run. Success requires the formal PASS marker,
current adaptive PASS markers, original waveform marker and exact input-readback
marker, in addition to a zero process exit status and matching executable hashes.

## Native-window gate remains separate

Do NOT run the whole desktop test suite on the user's desktop or set
`GITHUB_ACTIONS=true` / `GLASS_CI_NATIVE_FIXTURE=1` to enable the hosted-CI fixture.
The native fixture intentionally injects actual mouse input over its own windows
and requires an exclusively owned hosted desktop. The local build entry point
clears those authorization variables only in its temporary child process and
restores its inherited environment on return.

The previous native fixture failure and subsequent continuous-presentation
correction still require their own authorized validation. Local offscreen success
must not be described as final DWM display, native mouse-routing, latency/FPS,
visual acceptance, or a new live voice-session pass.

## Review artifacts and failures

`review.zip` contains only this invocation's test-generated frames, metrics,
compiler/self-test logs and `result.json`. It excludes user settings, desktop
captures, repository contents, caches and the large executable. The formal EXE
stays in the adjacent `product` directory with build information on success.

On a test/build failure the command returns nonzero, preserves evidence, and
emits the same optional attachment marker. Inspect that evidence, fix source
on GitHub, then synchronize/build again. Do not lower acceptance thresholds or
change source locally merely to make a check pass.
